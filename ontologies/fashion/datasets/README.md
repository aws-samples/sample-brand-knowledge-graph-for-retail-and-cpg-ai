# Data sets of the fashion domain

Each folder here is one **data set**: a brand with its catalog, looks and texts. The stack's graph
loader loads every data set of the graph's domain into Neptune Analytics once, at deploy, and the
app lists each set's examples (photos and texts to try) next to the domain's own in
[`../examples/`](../examples/). Add another folder here and the next deploy loads it too; the
brands are combined in one graph.

The sample ships two sets: `velloway/`, the synthetic catalog of the fictional brand Velloway,
generated by `ontology-rag synth` from `backend/src/ontology_rag/synth.py`; and `whimsikora/`, one
look of a second fictional brand with white sneakers, which the sample's example question is about
(see its README).

## Layout of a set

```
<set>/                 the set id: lower-case letters, digits, - and _, starting with a letter
│                      or digit, at most 64 characters
├── README.md          required: the app lists a set by this file
├── brand.json         the brand's id, name and description, shown in tab 0's Meet the brand (part of the catalog format, optional for a style DNA export)
├── domain.json        optional: example_questions, photo_questions, query_examples, added to the domain's lists
├── <data files>       loaded at deploy, in one of two formats (below)
├── media/<sub>/       optional: the data's own photos (for example looks/, products/), served by key
└── examples/          optional: inputs to try, the same shape as the domain's ../examples/
    ├── images/        whole photos (+ manifest.json), listed in tabs 1 and 2 (tab 6 for "batch": "new-work")
    ├── items/         single pieces (+ manifest.json), offered in tab 5's Style recommendation
    └── articles/      texts (+ manifest.json), listed in tab 2
```

`media/` and `examples/` hold different things. A photo in `media/` belongs to the data: a look or
a product of the catalog names it, and the app shows it next to that node. A file in `examples/`
is something to try in the app; the deploy does not load it into the graph (tab 2 ingests it when
you ask). Give an example a file name that no other example of the domain or its sets uses: the
app lists the domain's examples first, then each set's, and skips a file whose name is listed
already.

Two formats:

- **Catalog**: `brand.json`, `lines.json`, `items.json`, `looks.json`, `pairing_rules.json`,
  `articles.json`, the shape `synth.py` writes. The loader embeds every item, look and article
  statement at deploy with the embedding model and fills the product catalog index from
  `items.json`. A look's `occasion` text is matched to the ontology's occasions (its labels and
  hidden labels; a text such as `evening / formal` is tried facet by facet), and the look gets a
  `FOR` edge to the first that matches; a look that matches none keeps its text, gets no edge, and
  the load lists it as unresolved.
- **Style DNA export**: `graph.json`, `vectors.json` and optionally `catalog.json`, a graph exported
  with its vectors. The loader MERGEs the graph, writes the stored vectors as they are and fills the
  catalog index from `catalog.json`, so the set loads without a model call.

A node's or a catalog row's `image_key` of the form `<set>/<sub>/<file>` names a photo at
`<set>/media/<sub>/<file>` (`whimsikora/looks/<file>` is `whimsikora/media/looks/<file>`). In the
data bucket that is `ontologies/<domain>/datasets/<set>/media/<sub>/<file>`.

An example photo marked `"batch": "new-work"` in a manifest is a photo the graph has never seen:
only tab 6 ("Is this new photo on-brand?") offers it, tabs 1 and 2 leave it out.

## Who reads what

- The graph loader reads a set's data files, once, at deploy, and writes the graph and the catalog
  index from them.
- The photos under `media/<sub>/` stay in the stack's data bucket; the API reads one by key when
  the app shows it.
- The functions that serve requests carry only a set's `README.md`, `domain.json` and the files
  directly in `examples/<kind>/` (photos, texts, manifests), never its data files or `media/`, so a
  large set adds nothing to their cold start.
- The loader re-runs on a deploy when a `.ttl` or `.json` file of the domain folder changed (a
  new set brings its `.json` files) or the loading code did (`loader.py`, `dna.py`, `ontology.py`,
  `owl.py`, `kg.py`, `service.py`, `payoff.py`); a change to photos alone does not reload the graph.
